# T03 remote document route and reconciliation limit

Pinned Core source `cd12ddd88bc11490228343291dc1096c9ed3bf77` supports `doc.get` and `doc.set` with optional `on` (`schema/hc.openrpc.json`, `crates/herdr-core/src/api.rs:125–130`). Its router matches `on` against a saved machine's permanent `Machine.id` or mutable name while holding the catalog lock (`crates/herdr-core/src/remote.rs:744–779`). The forwarded call removes `on` before the remote Core handles the document. This ID route differs from the name-only `machine.connect`, `machine.rename` and `machine.rm` actions in G-MACHINE. Core mirrors a remote `doc` notice with the current machine **name**, and emits `missed` when its remote mirror resubscribes after a gap (`remote.rs:343–347, 455–477`). A notice alone supplies no document value; the client must refetch.

The new opt-in `remote_document_reloads_by_core_id_after_hub_and_machine_reconnect` test uses two isolated pinned Core processes and the existing test-only `HC_SSH` pipe into the remote Core. Spaceport starts no SSH process. It subscribes through `CoreBackend::watch`, writes a valid `spaceport` JSON document on the remote, and sees the hub's `DocumentInvalidation { machine: Some("lab"), name: "spaceport", version: 1 }`. It stops only its private hub child, writes version 2 on the still-running remote while the hub is disconnected, restarts that hub, renames the saved machine to `work`, then reads version 2 through `doc.get(on=Machine.id)`. The machine ID remains equal across the rename. It stops only its private remote Core child, waits until the hub catalog no longer calls that ID connected, then restarts it; the hub's `CoreChanges::next_batch` reports `missed`. A later remote write produces a document notice under `work`, and `doc.get(on=Machine.id)` returns version 3. The hub's local `spaceport` document remains at version 0. The fixture uses bounded private `server stop`, resets its cleanup flag when restarting, and reaps both exact children.

The app-global `core_terminals/observation.rs` still watches only the local hub document: `needs_document` ignores notices with `machine: Some(_)`, and its worker calls `doc_get("spaceport", None)` on initial, missed and local document events. The current Workspaces sidebar reads only that local document. There is no selected Core machine document consumer or approved policy for showing remote-owned group documents beside the hub-owned cross-host groups. Adding an unused per-remote map would create a second presentation authority without a reader. The next app slice needs one real remote group reader that requests a specific permanent machine ID, fences its epoch and stale status, and refetches by ID on remote notice, missed and reconnect; a mutable notice name must never become the write target. No Core API addition or client SSH fallback is needed for the document route. G-MACHINE still blocks name-only machine mutations, not ID-targeted `doc.get/set`.
