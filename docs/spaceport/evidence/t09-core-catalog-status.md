# T09 cached Core catalog status

At application revision `ef75bd1c`, `status` and the local control socket already supported `--json` and `--window`. The server rejects an explicit window ID that does not exist before dispatch (`control/server.rs::named_window`); it does not fall back to another window. The existing `status` reply showed legacy window hosts but no Core catalog freshness. The app-global Core observation already reads `machine.list` off the UI thread and clears machine rows on disconnect (`core_terminals/observation.rs`). No new backend call or subscription is needed for this inspection.

`status` now includes `core_catalog` in text and JSON. It reports the observation epoch, one of `not_started`, `synchronizing`, `current`, `disconnected` or `unavailable`, and a machine count only for a current catalog. `current` with count zero differs from an absent catalog. The unavailable error is a fixed class such as `refused` or `timeout`; Core's arbitrary diagnostic text is not echoed. The reply contains no machine rows, transcripts, terminal history, credentials or backend mutation. The control protocol version is 12 because the reply shape changed. Older status replies without this optional field decode as `not_started` under the new client.

The protocol test first failed to compile because `Status.core_catalog` and its types were absent, then passed 1/1 with `CARGO_TARGET_DIR=/tmp/spaceport-t00-target CARGO_INCREMENTAL=0 cargo +1.99.0 test --locked -p sheprd-control-protocol status_core_catalog_keeps_unknown_distinct_from_an_empty_result`. The focused headless app tests passed 5/5 with `cargo +1.99.0 test --locked -p sheprd-gpui --bin sheprd core_catalog`. They cover missing, pending, current empty, stale, a long typed Core refusal, bounded CLI text, and protocol decoding. A cross-platform local socket test passed 1/1 with `cargo +1.99.0 test --locked -p sheprd-gpui --bin sheprd status_refuses_a_missing_explicit_window_over_the_local_socket`: an explicit nonexistent window ID gets `NotFound`. Production `cargo +1.99.0 check --locked -p sheprd-gpui --bin sheprd` passed. These GUI commands used the same target and `CARGO_INCREMENTAL=0`. Existing macOS linker `__eh_frame` and `block v0.1.6` future-compat notices appeared.

No native CLI run or large-session budget measurement ran. A39 and A41 keep `not_run`; the linked evidence covers only the local slice. T09 remains in progress: unifying the wider GUI/CLI command catalog and proving full diagnostics behavior still need work. This status command reads the cached Core projection and does not confirm machine actions or session parity.
