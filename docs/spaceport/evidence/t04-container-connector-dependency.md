# T04/RM-CLOUD: saved Container connector cut boundary

Source audit of `42664731` using the T04 packet, the prior [Container cut order](t04-container-cloud-cut-order.md), [stop/destroy cut](t04-container-stop-removal.md), and the current [removal matrix](removal-reachability-54cb41c2.md). No app code, Core, saved file, Docker/Podman engine, or user state was changed. T04 remains blocked on G-LINK; T03 is `in_progress`, G-MACHINE is open, and A30 is `not_run`.

## Why a connector-only deletion is unsafe

- `sheprd-client/src/discovery.rs` has one `CloudProvider` variant, `Container`, and a `ConnectTarget::Cloud` whose account, ID and session are the saved connector's exact target. `sheprd-remote/src/cloud/providers.rs` dispatches that target to `container/connect.rs`; `container/machine.rs::ensure_running` may start it. `sheprd-gpui/src/connection.rs::start` dispatches every Cloud target there. Replacing that connector with a refusal would leave a visible device that cannot connect.
- `sheprd-gpui/src/endpoint/catalog.rs::cloud_devices` reads the client-owned `cloud-devices.json`; `reconcile_devices` converts each known saved row to a selectable endpoint and retains an existing Cloud endpoint after an unreadable catalog. The device picker, host menu, sessions, and status projection read those endpoints (`menu/devices/picker.rs`, `menu/devices/host_menu.rs`, `menu/sessions.rs`, `devices_overview/model.rs`). Hiding the Add Device provider rail alone would not retire saved endpoint selection.
- Container is the sole provider in `CloudProvider::ALL`. `settings_window/cloud_devices.rs::first_tab` indexes `[0]`; `main.rs` rejects `cloud` without `container`. The provider rail and catalog (`menu/devices/{rail,catalog}.rs`), Settings cloud section/card, host-menu saved-row actions, `cloud_setup` tick, and generic cloud code are tied to that same feature. Removing the variant requires a coherent cloud-feature and view/catalog cut, not an empty provider enum, dormant refusal or a misleading Settings tab.
- `docs/spaceport/plan/tasks.json` still marks T03 view projection `in_progress`. The shared endpoint reconciliation and selection code above is part of that view path. A coherent removal must coordinate with its new view keys and prove retained Core/manual-SSH selection. G-MACHINE has no atomic Core machine ID guard for connect/rename/remove, so old Container IDs must not be reinterpreted as Core machines or routed through mutable Core names. G-MACHINE is not a prerequisite for deleting this excluded provider.

## Saved data contract for that cut

`sheprd-remote/src/cloud/catalog.rs` parses known providers as `SavedDevice` and other provider keys as `Foreign`; it writes foreign records back as structured JSON. Its current tests preserve retired Boxd/Daytona rows beside an active Container row. They do **not** prove that `provider: "container"` becomes foreign when Container is retired. With no other provider left, removing the whole cloud catalog instead leaves `cloud-devices.json` untouched; that must be proved in a private HOME fixture across startup and ordinary retained device actions. Neither the catalog nor the Container engine may receive a delete/stop call. The separate `sandbox-images.json` catalog and old `[container]`/`[cloud.container]` config keys also remain user data; no automatic rewrite is authorized.

## Next coherent test boundary

First assert that an old Container row with its exact ID, account, machine, session, and unknown fields is not offered as a device, and that its source bytes survive startup and retained Core/manual-SSH actions. In the same red→green unit, retire the cloud provider rail, Settings/card, saved endpoint reconciliation and host-menu routes, `cloud_setup` and generic cloud workers, `ConnectTarget::Cloud`, provider connector/start, feature wiring, orphaned assets/messages/tests. Retained checks must cover Core machine catalog/selection, manual SSH, exact tab target, terminal/chat views and file actions, plus default/all-feature builds. Do not make the connector unreachable only by a feature flag while leaving its implementation shipped.

This audit ran source and package checks only. It makes no claim that Container support or RM-CLOUD is removed.
