## Reachable graph

- The Herdr 1 `ClientShellSnapshot.commands` wire field includes `ClientShellCommandAction::PluginAction` (`sheprd-protocol/src/wire.rs`). The app reads the same command list for palette entries, direct and prefix shortcuts, the Settings > Keybinds reference, and local CLI `keybinds`. Palette and shortcut activation send `command.invoke` through `sheprd-client`; plugin actions also attach the focused terminal selection. Removing only the named variant would break the wire contract while the Herdr 1 client still decodes those snapshots. The other custom action kinds share the same dispatch, so deleting the whole command path requires a retained shortcut/command projection first.
- Settings > Plugins is a separate `Section::Plugins` page with a catalog row, search field, `controls/plugins.rs`, `plugin_values.rs`, English Fluent messages, mockup captures, and GPUI tests. It reads custom agent/workspace tokens and status labels from the selected Herdr 1 host snapshot. Its switches edit the shared Herdr `[ui.sidebar]` rows and `[usage] inline` setting. Ordinary Sidebar settings and rendering also use that row layout; those are retained customization, so the shared parser, tokens, styles, and row writer cannot be removed with the plugin page by name.
- The legacy snapshot also carries plugin-selected agent order and view labels used by the ordinary sidebar and tab title. Terminal link resolution/activation can route clicks to Herdr plugin handlers. A plugin-created terminal or popup uses the ordinary terminal path. These are additional Herdr 1 reachability, not evidence that the Core path needs a client plugin engine.
- There is no client plugin crate or plugin package hook in this cut. No explicit `plugin` command exists in the local CLI/control protocol. The CLI `keybinds` response still exposes daemon custom bindings; `docs/cli.md`, the GPUI README, config example, and English settings messages describe the old behavior. This inventory did not inspect every translation or build target.
