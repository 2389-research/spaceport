# T04: page new-window requests are denied

At integration `b49ad18da`, the remaining production `Store::open` call for a web page was `browser::view::open_beside`. A page's `window.open` or new-window link reached it through `Event::NewWindow`; on macOS, `native::new_window` could first build a linked WebKit popup and `Event::Opened` adopted it into a tab. The first T04 popup cut removed popup creation but sent the requested URL to GPUI's system handler. Review found that script can call `window.open` without a click, so that outward action breached the explicit user-action boundary. The follow-up makes the Wry new-window handler deny every request without queueing an event, adding a tab, or opening a system URL, including when the address is valid HTTPS. The popup builder, adoption, delegate, close queue, and popup-only error remain removed.

TDD: the new headless `page_new_window_does_not_open_a_valid_https_url_or_create_a_tab` failed against the first cut because the handler's queued event opened a system URL. It now passes and checks `NewWindowResponse::Deny`, no system URL, unchanged tab count, and the retained source page. A native unit test checks the same denial with no queued event. The request path supplies no user-gesture proof, so no new-window address can be handed to the system opener here. Explicit chat HTML, terminal links, and service URLs continue through their existing click handlers. No real browser, personal URL, user data, or Core repository was used.
