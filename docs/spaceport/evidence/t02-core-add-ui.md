# T02 Core Add Device form

Pinned Core `cd12ddd88bc11490228343291dc1096c9ed3bf77` accepts `machine.add` with `target`, optional `name` and `session`, and `temporary`; its `install` flag is CLI-only and skipped by serde (`crates/herdr-core/src/api/types.rs:731–760`). The handler validates the target/name, probes an existing remote Core, then rechecks name and remote ID before saving (`api.rs:612–672`). Every `RpcError` return precedes `st.machines.push`, so a typed refusal means this request did not add a machine. Core's SSH probe uses `BatchMode=yes` and can wait 20 seconds for hello (`machines.rs:245–391`); the client call timeout is 10 seconds (`crates/sheprd-core-client/src/connection.rs`). A timeout, lost connection, malformed answer or result without an ID cannot prove whether Core saved the machine.

The familiar three-field Add Device form now copies target, label and session at submit and dispatches only `Core::machine_add` on a detached worker. It does not use the old probe, saved-host catalog, installation offers or host-key skip. A Core refusal keeps the form open with bounded, control-stripped message and hint; Core still owns SSH trust and credentials. The app-global gate allows one add at a time across windows. Confirmed success with a nonempty Core ID, pre-dispatch `Unsupported`/`Busy`, or Core `Refused` releases it. Any uncertain result keeps the submitted request blocked for the process lifetime, including after dialog/window close. A second window never sends another add while the gate is in flight or unknown. Catalog name/target matches cannot attribute an unconfirmed request, so the UI does not auto-clear the gate. Restarting Spaceport loses this in-memory gate and does not prove the outcome; the warning says so. When no local Core is connected, the form asks the existing hub to join one without installing or starting a bundled Core, and reports failure explicitly.
