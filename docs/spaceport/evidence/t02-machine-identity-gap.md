# T02 exact machine target gap

Pinned Core source `cd12ddd88bc11490228343291dc1096c9ed3bf77` exposes a permanent remote Core `Machine.id` beside a mutable local `Machine.name` (`crates/herdr-core/src/machines.rs`; `api.rs:639–667`). Its `machine.list` returns both. The live two-Core fixture in `crates/sheprd-core-client/src/tests/live/machines.rs` proved that a rename keeps the ID and changes the qualified address, and that remove leaves the remote terminal running. The scripted tests in `tests/machine.rs` and `tests/machine_manage.rs` prove the client currently sends name-only Connect, Rename and Remove requests. These tests did not exercise concurrent name reuse.

Core's schema and handler accept only `machine` (a name) for Connect and Remove, or `machine` and `new_name` for Rename (`crates/herdr-core/src/api/types.rs:762–774`, `api.rs:681–723`; source S03/S12). Each handler selects `m.name == p.machine`. If another Core client renames selected machine A and assigns A's former name to machine B before the GUI request arrives, a saved name can reach B. A fresh `machine.list` before dispatch and a returned-ID check after dispatch cannot close that race. For Remove, the returned value is only the removed name, so even the post-action check is unavailable.

**Smallest external dependency G-MACHINE:** Core must accept a stable machine ID or an atomic expected-ID guard with the name on `machine.connect`, `machine.rename` and `machine.rm`, checking identity under Core's catalog lock before any side effect. Update the source schema and client together. A private two-client fixture must rename/reuse a name between GUI selection and dispatch, then prove Core refuses the stale identity and leaves B unchanged. Do not route these actions through legacy SSH or Herdr 1. T02, T07 host actions and A04 remain blocked; the separate read-only catalog and Core-owned aggregation evidence remain valid.

The smallest independent GUI work is to adapt the existing Add Device form's target, label and session fields in `menu/devices/add_device.rs` to one background `Core::machine_add` call, with Core's returned ID as the result. The current `setup::claim/probe/save`, host-key skip, terminal installer offers, `HostMenu::Saved::Ssh`, `setup::rename/remove` and `endpoint::reconnect` belong to the legacy path (`add_device.rs`, `setup.rs`, `host_key_choice.rs`, `host_menu.rs`, `endpoint.rs`). Keep the familiar form and confirmation UI, but do not retain those routes as Core actions. Core's RPC add does not install a remote Core; SSH uses noninteractive `BatchMode=yes` and returns refusals such as `needs_login`, `unreachable`, `hc_missing` or `incompatible` (`machines.rs:245–391`). The client currently drops Core's `data.hint` (`sheprd-core-client/src/connection.rs:57–79`), so preserving and showing that typed hint is an in-repository prerequisite for actionable trust/auth refusal. Its 10-second call timeout can also precede Core's 20-second remote hello; a timed-out add has an unknown outcome and must be reconciled from the catalog, never blindly retried.

Existing GUI test seams are `menu/devices/tests/core_catalog.rs` for the Core projection, `menu/devices/tests/host_key.rs` and `key_login.rs` for the legacy trust flow, and `menu/devices/host_menu/tests.rs` for rename/remove confirmation. New headless scenarios should assert exact ID remains attached to the selected row across catalog reorder, Core refusal keeps the form and target, and timeout shows uncertain outcome without another mutation. The private Core fixture must cover add and auth refusal, then ID-guarded Connect/Rename/Remove once Core supplies that contract. No new application or native test ran for this source-only finding.
