# RM-PHONE reachability and extraction boundary

Read-only inventory at `e6250fc0`. This begins the RM-PHONE audit; it does not remove phone behavior, test a native app, or satisfy A30/A54. T04 stays `in_progress` and T10 stays `not_started` until its prerequisites are met. No personal service, daemon, credential, or Core state was read or changed.

## Reachable graph

- Normal GUI startup installs `remote::Supervisor` and `device_tags::DeviceTags` (`sheprd-gpui/src/app.rs`). The supervisor reconciles a user service with `[remote]` settings, polls the phone daemon, starts the nearby helper, and follows app update/status state (`remote/supervisor.rs`). The GUI also exposes a phone status icon, pairing/revoke dialogs, Settings > Remote control, and `RemotePair` in the command catalog. The private desktop CLI/control protocol has `remote status/pair/devices/restart/revoke` (`cli/control/remote.rs`, `control/server/remote.rs`, `sheprd-control-protocol/src/protocol/remote.rs`). The desktop local control socket itself is retained.
- `sheprd-remote-control` is both the phone HTTPS/push server with its default `server` feature and a `default-features = false` app/control library used by GPUI and `sheprd-control-protocol`. The latter dependency supplies phone device/status/pairing types, service management and tags (`sheprd-remote-control/src/{lib.rs,app,control}`). The `server` side also reads Core chats (`hub/core`); that does not make the phone listener a retained Core endpoint.
- `sheprd-gpui/src/device_tags.rs` keeps a local tag copy used by the sidebar, host menu and status bar; `device_tags/sync.rs` exchanges it with phone daemons, including an SSH command that searches for `sheprd-remote-control`. Those display and edit sites need an explicit decision against the Core machine catalog before the daemon dependency can be cut. Retain Core machine display; do not keep the phone sync loop as a second registry.
- Bluetooth phone pairing/presence uses `sheprd-gpui/src/remote/nearby`, `crates/sheprd-nearby` on Linux/Windows, and `macos/sheprd-nearby` on macOS. The separate Add Device > Nearby list in `sheprd-gpui/src/menu/devices/discover.rs` gathers Bonjour, Tailscale and SSH suggestions for machine setup. Its source is not the phone Bluetooth helper. SPEC.md:33 requires manual address/alias entry and no discovery, so this list needs a separate deletion audit; preserve the manual host-manager form and Core machine display.
- `Justfile`, `.github/workflows/{ci,release,ios}.yml`, `scripts/release` package/build/signing/SBOM files, and `ios/` still build, bundle, test or publish phone binaries and mobile clients. The candidate `crates/sheprd-apns` and `crates/sheprd-push-relay` directories are absent at this revision; APNs/push code is inside `sheprd-remote-control`. This inventory has not exhaustively checked every platform asset or dependency.

## Coherent deletion unit and future proof

First map the retained Core machine view and decide whether local tags remain a Spaceport presentation preference. Extract any kept pure tag normalization/data type from the phone crate, or delete the tag UI if it is solely phone-owned. Then remove the phone service supervisor, dialogs, status/settings/CLI/control paths, phone-specific config/assets/messages/tests, helper and server crates, iOS/watch targets, and all build/package hooks together. Keep the private desktop IPC and ordinary Core machine/terminal/chat behavior. A stale `[remote]` config must activate no phone behavior, and the `remote` CLI command must be unavailable; a fixture startup must create no phone service/helper or remote tag sync. Retained checks should cover local IPC, Core machine display, and manual Add Device controls. No such tests were run in this audit.
