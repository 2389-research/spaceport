# T03 Core document edit service slice

Source: Spaceport worktree based on `3a7388e89c5a0acdc277aef5eb9213240d2ab14c`; pinned Core `cd12ddd88bc11490228343291dc1096c9ed3bf77`. Core's `api/doc.rs` checks the expected version before it writes and returns `kind: "conflict"` for a stale version. The client already exposes typed `doc.get` and `doc.set`; no workspace RPC was added.

The blocking edit service under `core_terminals/workspace_document` takes a parsed document with Core's version. Create, rename, archive and delete change only the local `spaceport` value. A successful `doc.set` returns the new version and value. Only a typed `doc.set` conflict triggers a reread and one retry: creation requires the new ID still absent; edits to an existing workspace require its complete record, including unknown fields, to match the caller's base. The retry applies the edit to the latest document, preserving disjoint changes and unknown fields. A second conflict refuses. Timeouts, lost connections and other refusals keep their original typed Core errors and are never retried; their outcome may be unknown.

The old workspace menu and dialogs still consume `ClientShellSnapshot` and call legacy `workspace.*` methods. They have no Core document target. This service is not wired to those controls, and the observer's document/version/error has no real workspace UI reader yet. The narrow next seam is a Core workspace action worker that takes a **fresh** observer document/version, calls this service, then lets the one existing Core observer reconcile the resulting document notice. UI work must also present stale/invalid-document errors and avoid queueing offline edits. No second document copy or subscription is needed.

The service and its private Core contract tests do not complete A06 or A07 because the actual retained UI path is still legacy. A08, A09, A24 and A53 remain `not_run`. Remote document watching and the native lifecycle cases are outside this slice.
