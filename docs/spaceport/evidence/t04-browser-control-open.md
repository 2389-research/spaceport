# RM-BROWSER: local page-open control route

At parent `ff53b00c`, `browser open` had a separate local CLI/control route: `cli/control/browser.rs` parsed it, `control/client/browser.rs` built `Request::Open`, `control/server/browser.rs` selected a window, and `browser/view/requests.rs` created a page tab. This cut removes that route, its `BrowserOpen` and `Opened` wire types, obsolete placement logic and request-only tests. The control protocol version rises to 14 because the accepted request and response shapes changed. A new wire test rejects `browser.open`; a new CLI test rejects `browser open` before starting the GUI. The socket framing tests now use retained `browser.reload` messages.

`menu/devices/host_menu/forwards.rs` still offers Open for a listening SSH forward. It sends the exact `Forward::url` loopback address to the GPUI system URL handler and does not create a page tab. Its isolated headless test clicks the real menu row and checks `http://127.0.0.1:39876/`. The forward worker and Core port ownership do not change. `control_target` and `Target` stay because host, work, and tab commands use them to reject another daemon's workspace; a headless test keeps that strict refusal.

The SSH metadata shim in `remote_browser/herdr-gpui.sh` and `remote_browser/window.rs` can still ask a connected window to make a page tab. Saved `browser-tabs.json`, tab operations, reload, feedback, review notes, native webviews, annotations, assets, and dependencies remain. These are later coherent graph cuts. Neither this change nor the host-forward menu proves a Core service-forwarding route (G-PORT). T04/RM-BROWSER stay in progress; A28/A29 remain not run. No real browser, network, daemon, or native UI ran.
